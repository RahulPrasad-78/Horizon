A step-by-step guide for beginners. It explains what every part does, how a click in the browser travels through the gateway to the backend services, and how they talk to each other and to the database.

Built with .NET 10 · YARP gateway · 5 microservices · MVC website · PostgreSQL (Neon) · Serilog logging

1The big idea

One website, many small programs working together.

Horizon is an online learning platform. Students browse and enrol in courses, teachers create courses, and students and teachers can chat. Instead of building this as one big program, it is split into small, independent programs called microservices. Each one does one job and owns its own database.

🏨 Think of a hotel The website is the guest. The gateway is the reception desk: every request goes there first, and reception checks your key card and sends you to the right department. The services are the departments (housekeeping, restaurant, spa…). Each department keeps its own paperwork (its database). Departments can also phone each other when they need something.

The main point of the project is the gateway: the browser never talks to a service directly. Everything goes through one door (https://localhost:7000), which makes it easy to add security, limits and logging in one place.

5Follow one request: “a student enrols in a course”

This single click touches almost every part of the system.

  1. Browser → MVC. You press Enrol. The browser sends your session cookie to the website on port 7006.
  2. MVC → Gateway. The MVC controller uses a pre-configured HttpClient named StudentAPI whose base address is https://localhost:7000/students/. A helper called BearerTokenHandler reads your JWT from the session and adds the header Authorization: Bearer <token>.
  3. Gateway. It matches the path /students/**, removes the /students prefix, applies the rate limiter, and forwards POST /api/enrollment/1 to https://localhost:7002.
  4. Student service. It validates the token itself, takes your user id from it, then asks the Course service whether course 1 exists (GET api/coursesapi/1).
  5. Student service → database. It stores the enrolment in its own database, horizonStudentDB.
  6. Student → Course. It tells the Course service about the enrolment with POST api/coursesapi/enroll. This call is not made by a person, so it proves itself with the shared secret header X-Service-Key. The Course service saves it in horizonCourseDB.
  7. The answer travels back the same way: Student → Gateway → MVC → Browser, and the page updates.
Why save it twice? Each service owns its data. The Student service needs “which courses am I enrolled in?”, while the Course service needs “how many students joined this course?” (the teacher dashboard reads that count). Keeping a copy in each service means one can keep working even if the other is slow.

Example: calling https://localhost:7000/courses/api/CoursesApi reaches the Course service as GET /api/CoursesApi. The first path segment is the “address label”; the gateway peels it off.

One route, as configured

"teacherRoute": {
  "ClusterId": "teacherCluster",
  "Match": { "Path": "/teachers/{**catch-all}" },
  "AuthorizationPolicy": "default",     // must carry a valid JWT
  "RateLimiterPolicy": "fixed",         // 100 requests per 10 seconds
  "Transforms": [ { "PathRemovePrefix": "/teachers" } ]
},
"teacherCluster": { "Destinations": { "d1": { "Address": "https://localhost:7001/" } } }

What happens to every request, in order

  1. Serilog request logging: one log line per request.
  2. Authentication: if an Authorization: Bearer … header exists, the gateway checks the token’s signature, issuer, audience and expiry.
  3. Authorization: routes with the default policy (teachers, chat) reject you with 401 if there is no valid token.
  4. Rate limiter: more than 100 requests in 10 seconds gets 429 Too Many Requests (up to 10 extra requests wait in a queue).
  5. Reverse proxy: YARP forwards the request, and sends the answer back. If the target service is off you get 502.
The gateway passes your Authorization header through unchanged, so each service can check the token again. That way a service stays safe even if somebody calls it directly, bypassing the gateway.

7Login & security

Code: services/identity-service/

Register and login flow

  1. Register – POST /auth/api/Auth/register with email, password and role (Student or Teacher). Identity creates the user in horizonDB with a hashed password.
  2. Students can log in at once, and Identity also calls the Student service (POST api/profile/seed/{id} with X-Service-Key) so the new student gets a profile automatically.
  3. Teachers have to wait: logging in returns 401 “Pending approval” until an Admin approves them on the admin page (approve-teacher/{id}).
  4. Login – POST /auth/api/Auth/login returns a JWT, valid for 60 minutes. It contains your user id, email, roles, issuer KrishTanwar, audience Students/Teachers and an expiry time, all signed with a secret key.
  5. The MVC website keeps the token in the session and in an HTTP-only cookie, and signs you into the site with a normal cookie for 2 hours.

What is Polly? A library that automatically retries a failed call a couple of times. If the other service still does not answer, the caller logs a warning and returns an empty result instead of crashing.

9Inside one service

Every service is built in the same layers, so once you understand one you understand all.

FolderWhat lives there
Controllers/The URLs (endpoints) the service offers.
DTOs/“Data Transfer Objects”: the exact shape of the JSON going in and out.
Validators/Rules such as “title must not be empty”. They run automatically before the controller code.
Services/The real logic (e.g. “can’t enrol twice”).
Repositories/Database reads and writes.
Data/The DbContext: the list of tables and their rules.
Models/The C# classes that become database tables.
Migrations/Auto-generated recipes that create the tables.
Middleware/Global error handler: turns exceptions into tidy JSON errors.
Mappings/AutoMapper rules (identity, course, chat).
Program.csThe start-up file: wires everything together and starts the web server.
Example: trace GET /api/chat/history/1 through the Chat service
  1. Program.cs → Serilog request logging, then ExceptionMiddleware wraps everything in a safety net.
  2. ChatController.GetHistory(1) receives the call.
  3. It asks ChatService.GetHistoryAsync(1).
  4. That asks ChatRepository.GetChatHistoryAsync(1), which runs an EF Core query for messages of the last 15 days.
  5. AutoMapper converts Message rows into MessageResponse objects, which return as JSON.

10Databases

One PostgreSQL server (Neon), four databases – one per data-owning service.

DatabaseOwnerMain tables
horizonDBIdentityAspNetUsers, AspNetRoles, AspNetUserRoles… (ASP.NET Identity standard tables)
horizonCourseDBCourseCourses, CourseVideos, Comments, Enrollments
horizonStudentDBStudentStudentProfiles, Bookmarks, ProgressRecords, Enrollments
horizonChatDBChatUsers, ChatSessions, Messages
  • No service reads another service’s database. They only ask each other through APIs.
  • Tables are created automatically. Each service runs Database.Migrate() when it starts, applying the InitialCreate migration from its Migrations/ folder if the tables are missing. Identity also seeds the admin account at that moment.
  • The code uses UseNpgsql(...) (the PostgreSQL driver) in each Program.cs.
Course and Identity stop if the database is unreachable (they cannot run without one). Student and Chat only log an error and keep running, so check their logs for “error occurred while migrating” if data is missing.

11Where settings come from (connection strings!)

Why appsettings.json shows a fake password but the app still reaches Neon.

When a .NET app starts, WebApplication.CreateBuilder(args) reads settings from several places, later ones win:

  1. appsettings.json (in the repository): holds a harmless placeholder Host=localhost;…;Password=CHANGE_ME.
  2. appsettings.Development.json (if you create one).
  3. User-secrets (only when ASPNETCORE_ENVIRONMENT=Development): a private file on your computer at
    %APPDATA%\Microsoft\UserSecrets\<UserSecretsId>\secrets.json. The UserSecretsId is written in each service’s .csproj.
  4. Environment variables (e.g. ConnectionStrings__DefaultConnection). Handy for servers.
  5. Command-line arguments.

The code then asks for the setting by name:

// services/course-service/Program.cs
builder.Services.AddDbContext<ApplicationDbContext>(options =>
    options.UseNpgsql(builder.Configuration.GetConnectionString("DefaultConnection")));

Whatever source “won” gives the value. On your PC it is the Neon string from user-secrets.

ServiceSetting name
Identity, Course, StudentConnectionStrings:DefaultConnection
ChatConnectionStrings:WebApplication1Context

Set your secret

cd services/course-service
dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=ep-xxxx.neon.tech;Database=horizonCourseDB;Username=neondb_owner;Password=YOUR_PASSWORD;SSL Mode=Require;Timeout=30"
dotnet user-secrets list
Why not commit the password? Anything pushed to GitHub is public. User-secrets keeps the real password on your computer only. On a new PC you set the secrets again (4 commands).

14Run it yourself

  1. Install the .NET 10 SDK.
  2. Get a database. Create a free Neon project with four databases named horizonDB, horizonCourseDB, horizonStudentDB, horizonChatDB (or run a local PostgreSQL). See database_setup_neon.md.
  3. Set the four connection-string secrets (section 11).
  4. Trust the dev certificate once: dotnet dev-certs https --trust
  5. Start everything from the repository root: ./run-all.ps1 (opens 7 windows).
    Or in Visual Studio use integration.slnLaunch.
  6. Open https://localhost:7006, register, and explore.
  7. Log in as admin to approve teachers: the default admin is krish@learningplatform.com / Krish@123 (change it with Admin:Email and Admin:Password).
Each service also has an interactive API page at https://localhost:<port>/swagger (Development mode). The Chat service shows it on its root page.

15Try the API like a developer

These work in a terminal (use -k so curl accepts the local certificate).

# 1) Log in as admin through the gateway and keep the token
curl -k -X POST https://localhost:7000/auth/api/Auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"krish@learningplatform.com","password":"Krish@123"}'

# 2) Public data: no token needed
curl -k https://localhost:7000/courses/api/CoursesApi

# 3) Protected route without a token -> 401 from the gateway itself
curl -k -i https://localhost:7000/teachers/api/teacher/courses

# 4) Same route with a teacher token -> 200
curl -k https://localhost:7000/teachers/api/teacher/courses -H "Authorization: Bearer YOUR_TOKEN"

# 5) Watch the rate limiter: after 100 quick calls you start getting 429
for i in $(seq 1 140); do curl -sk -o /dev/null -w "%{http_code}\n" https://localhost:7000/students/swagger/index.html; done | sort | uniq -c

Good learning exercise: stop one service (say Course) and call its route through the gateway: you will see 502 from the gateway while the other routes keep working. That is the point of microservices.

16Known limits (good next steps)

  • Chat has no login check of its own. Only the gateway protects it, so call it through the gateway.
  • Most student endpoints are open (only /api/profile checks a token) and the student, course and auth routes have no gateway policy.
  • Course “progress” notification (api/coursesapi/progress) only logs the message; it does not store progress.
  • Teacher chat is a placeholder: the Teacher service returns an empty conversation list.
  • Secrets in appsettings.json: the JWT key, ServiceAuth:Key and admin password are plain values meant for local use. Move them to user-secrets or environment variables before deploying anywhere public.
  • No automated tests yet.
